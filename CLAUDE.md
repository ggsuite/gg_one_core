# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

`gg_one_core` is the foundation of the gg_one tool family. It bundles three concerns that every other package of the family builds on:

- **State kernel** (`lib/src/tools/`): `GgState` (hash-keyed check caching in `.gg/gg.json`), the `CommandCluster` base of all `can_*` commands, the `DidCommand` base of all `did_*` commands, `Suggestion`, `EnsureGgJsonNotIgnored` (keeps the tracked state file out of `.gitignore`), and the pubspec-overrides backup helpers.
- **Checks** (`lib/src/commands/check/`, `tools/analyzer.dart`, `tools/formatter.dart`, `tools/checks.dart`): the individual verification steps and the `Checks` container that `can commit` / `can push` run through.
- **Publish configuration** (`tools/repo_publish_config.dart`, `tools/publish_state.dart`, `tools/commit_message.dart`, `tools/publish_files.dart`, `tools/publish_config.dart`, `tools/version_selector.dart`, `tools/ensure_publish_config_ignored.dart`, `commands/do/do_configure_publish.dart`): everything around `.gg/publish_config.json` and `.gg/publish_state.json`. The two files split what used to be one: `publish_config.json` holds the **answers** (merge message, version increment, the AI-maintained `nextCommitMessage` and the recorded `commits`), `publish_state.json` the **run state** (status, done steps, branch, pr, channel, delete decisions, plus a copy of the merge message and increment the run started with — `do publish` deletes `publish_config.json` before its merge, and `loadRepoPublishFiles` fills the answers the config lacks from the state so a `--continue` asks nothing again) — so a `--restart` discards the run without discarding what the user chose. They are written in camelCase; the legacy snake_case `PublishConfig` is read-only now, bridged by `legacySplit(repoName)`, and `loadRepoPublishFiles` layers new over legacy without ever writing the old format again. `CommitMessage` owns the first-line rule (`validationError`): the first line must not be empty, its length is not limited (the former 60-character limit is gone; `maxCommitMessageFirstLineLength` is only kept, deprecated, for compatibility). The publish flow that consumes the config lives in `gg_one_do_publish` — its CLAUDE.md documents the end-to-end semantics.

  **Message sheet** (`tools/message_sheet.dart`, `tools/jsonc.dart`, `tools/commit_sheet.dart`): instead of one prompt per question and repo, `gg do commit`, `gg do review`/`publish`/`configure-publish` (gg_multi) and `gg one do commit`/`configure-publish` show the commit messages, merge messages and version increments of all affected repos as **one `.jsonc` file** in the user's editor (`GgPrompts.editText` → `ExternalEditor` in gg_interact). The sheet is only a view: defaults come from each repo's `publish_config.json` (else the ticket description), a field left empty keeps its default, and the answers are written back per repo. An unreadable sheet is reopened with the reason (line:column) on top; closing it unchanged again or saving it empty aborts. `Jsonc.stripComments` is length-preserving so parse errors point into the user's text. `commitSheetEntry` builds the entry `do commit` shows; `RepoPublishConfig.withCommitAnswers` decides what is recorded — the commit only when one was made, a merge message only when it differs from the default shown (a bare default would freeze the ticket description), an edited commit message of a repo that was not committed becomes `nextCommitMessage`. Without an editor (`editText` null — no terminal, an embedder, no editor found) callers fall back to the per-question prompts; `--no-interactive` takes the defaults.

### Settings (`tools/gg_rc.dart`)

`GgRc` is gg's one settings class: the user's `~/.gg_rc` (`$GG_RC` names another file) and a repository's `.gg/gg_rc`, one JSON object each with the same structure — keys follow the command path and end with the flag they preset (`{"do": {"add": {"transitive": false}}}`). Both may contain comments (`Jsonc.stripComments`). Precedence: command line > `.gg/gg_rc` > `~/.gg_rc` > built-in default; a flag given on the command line always wins, the files only replace the default.

- `builtInDefaults` — the settings of the user file. `GgRc.load(ggLog:)` writes the user file with them when missing (a folder that cannot be written only warns) and never rewrites an existing one. `repo:` reads `.gg/gg_rc` on top.
- `repoDefaults` — settings that belong to **one repository** and may only be set in its `.gg/gg_rc`: `do.upgrade.deps.majorVersions` (`GgRc.upgradeMajorVersions`) and `can.commit.checks` (`GgRc.commitChecks`), both `true`. `flag()` never reads them from the user file, and a user file holding one loads as broken (»set it in the .gg/gg_rc of each repository«). Since the user file cannot hold them, a repository file spelling them out hides no user setting.
- `GgRc.loadRepo(repo, create:)` reads only `.gg/gg_rc` — no home directory involved, safe in checks and tests. `create: true` writes a missing file with `repoDefaults` and adds `!.gg/gg_rc` below a `.gg/*` rule of the root `.gitignore`; without it nothing is written, so a check never dirties the tree.
- A file with invalid JSON or no object loads as broken (`error`): every `flag()` throws it, loading itself does not. `flag()` throws for a non-boolean value (naming the file that holds it) and for an unknown setting. `GgRc.defaults()` touches no file. `ReadSettings` is the function type `GgRc.load` fits.
- `CommandCluster(checksSetting:)` reads that setting with `loadRepo` (never writing) and, when it is `false`, records success without running its commands.

### gg's commit conventions live here

`tools/gg_commit_message.dart` (the `#gg: ` prefix, the legacy subjects, `isGgGenerated`, the merge-back prefix `PublishSkipCheck` anchors on) and `tools/gg_owned_files.dart` (`ggOwnedFileNames`/`ggOwnedRootFiles`/`isGgOwnedPath`) hold gg's own conventions. They sit here rather than in `gg_git` because they are *application* knowledge — what gg calls its commits, which manifests and lock files its bookkeeping may touch — not git semantics. `gg_one_core` is the lowest layer that sees both `gg_git` and `gg_lang`, and it already hosts the sibling list `GgState.ignoreFiles`; a test pins the inclusion `ignoreFiles ⊆ gg-owned` so the two cannot drift.

`tools/gg_system_commit.dart` (`GgSystemCommit`) is the one producer of every `#gg:` commit in the whole family. It splits the dirty tree by ownership, saves foreign changes in their own **prefix-less** commit first (message: injected builder → ticket description → `Save pending changes on <branch>`), then writes the pathspec-limited bookkeeping commit, and refuses to write anything outside a feature branch. **`keepForeignChanges: true`** skips the save commit and leaves the foreign changes uncommitted — for callers that commit gg's files *next to* the user's unfinished work (gg_multi_core's `TicketLocalizer`, which also passes explicit `paths`); `stateKey` is then only recorded when no foreign change is left, because a dirty tree is no »everything committed«. `lib/gg_one_core_test_helpers.dart` exports the two assertions that verify both invariants against real git history.

`tools/contributed_commits.dart` (`ContributedCommits.manualCommitReason`) is the one predicate for »did this ticket contribute work?«, shared by `gg do commit` (»✓ Nothing to commit« instead of an invented CHANGELOG entry) and gg_multi_core's `PublishSkipCheck` (skip the release). A `#gg:` commit is work when it touches a non-gg-owned file **or changes the set of consumer-visible dependency names of a manifest** (`pubspec.yaml` `dependencies`; `package.json` `dependencies`/`peerDependencies`/`optionalDependencies`, basename match at any depth, compared `<hash>~1` vs `<hash>` — `~1` because cmd.exe eats `^`). Constraint changes (`--tighten` upgrades, path/git/link rewrites), dev dependencies and `dependency_overrides` stay bookkeeping; a missing file declares nothing; an unparsable manifest counts as work. Reason: older `gg do add` swept the user's new dependency into `#gg: changed references to path`, and the repo was then skipped on publish — the dependency silently lost. For `gg do commit` this means: a clean repo whose only contribution is such a commit gets the CHANGELOG entry (it will be released).

helix's `#gg: generated DNA` commit (`ggGeneratedDnaMessage`) also owns the files its run generated: `dna/_generated.json` (`dnaManifestPath`), the root `CLAUDE.md` and every instance the manifest lists before or after the commit, never one below `dna/` (a DNA package ships that folder). The manifest is read only when a file is left that `isGgOwnedPath` does not cover. A test pins both constants to helix, which is only a dev dependency. Without this every ticket repo carried a DNA commit and no repo was ever skipped.

A system commit that replaces what `gg do commit` used to do must pass `stateKey: GgState.doCommitKey` — that is the one part of the contract the class cannot enforce for the caller. The recorded state hash covers the **content** of the tree, so a bookkeeping commit that rewrites a manifest (changed references, tightened constraints) invalidates it, while one that only touches lock files or `.gg/` does not (`GgState.ignoreFiles`). Forget it after a manifest rewrite and every gate reading the state through `gg did commit` — `gg can merge`, `gg can publish` — fails with a spurious »Not committed yet«. Leave it null when the commit is deliberately partial (explicit `paths`, or `includeUntracked: false`): the tree is still dirty afterwards and the recorded answer would be a lie.

The checks layer does not depend on the state kernel (no `GgState`, no `CommandCluster`) — that separation is intentional and worth keeping. All commands extend `DirCommand<T>` from `gg_args`; the primary logic lives in `get()`, and `exec()` delegates to it. `ggLog` is constructor-injected everywhere for testability.

## Behavior notes

### Checks

- **`check/`** — **no CLI group any more.** These are the individual verification steps `can commit` / `can push` run through the `Checks` container (`tools/checks.dart`); they were also exposed as `gg one check <name>`, which only duplicated what `can commit` does anyway. The `Check` group command is gone, the classes stay: `analyze`, `format`, `pana`, `package_json_scripts` (TypeScript npm scripts), `npm_logged_in` (npm auth before publish), `no_pubspec_overrides` (a `pubspec_overrides.yaml` must not redirect a dependency to a local **path** when publishing — part of `can publish`; `do publish` saves the file to the git-ignored `.gg/pubspec_overrides_backup.yaml` and deletes it up front — `tools/pubspec_overrides_backup.dart`, whose `backupPubspecOverrides`/`restorePubspecOverrides` also cover `pnpm-workspace.yaml` (backup at `.gg/pnpm_workspace_backup.yaml`) — pnpm-managed TypeScript repos carry their `link:` overrides there — and whose restore the publish flow calls at its end, once the feature branch is checked out again, so the workspace wiring survives the publish). A `git:` override does _not_ fail the check: older gg versions pinned every repo of a ticket to its feature branch that way (today's `gg do review` leaves the refs alone), and such a ref resolves for everybody, unlike a path. Both the check and its static `NoPubspecOverrides.hasLocalizedRefs(dir)` ask the same question »does this package still redirect a dependency to a working copy?« — a missing, empty, overrides-free file and one holding only git refs or version constraints all count as _not_ localized, an unparsable one as localized. `--merge-only` (below) — in gg_one and in gg_multi — uses it as its precondition

#### `pana` needs a released state to score against

Pana measures a package against what it published: it resolves the `repository:` URL and expects to find the package on the **default branch** at the version pub.dev serves. Before the first release neither side of that comparison exists — the feature branch was never merged, no tag was ever written — and pana reports problems the package itself cannot fix, which used to block `can publish` on exactly the release that would have fixed them. `Pana.get` therefore asks two questions first: **is there a version on pub.dev**, and **does this repository carry a version tag for that version**? Only a yes to both means a full release cycle happened here; anything else skips pana (»Skipping pana (not on pub.dev yet)« / »Skipping pana (no git tag `<version>`)«) instead of failing. The tags of the whole repository are consulted, not the ones on HEAD — pana runs from the feature branch, while the release was tagged on the default branch. The gate is unconditional: unlike `--published-only`, which only asks whether pub.dev is a *target* at all, this asks whether the package ever *arrived* there. Both `PublishedVersion` and `FromGit` are constructor-injectable, so tests decide the answers without touching the network.

### State caching and command bases

### State caching (`GgState`)

`lib/src/tools/gg_state.dart` manages the `.gg/gg.json` file. Each successful check stores a hash of the working-tree state so subsequent runs can skip re-running checks when nothing has changed. When only `.gg/gg.json` changed, it is committed automatically — amended into the last commit only when that is gg's own `#gg: …` bookkeeping commit that is not pushed yet, and as a new `#gg:` commit otherwise. **User commits are never amended silently**; consecutive state updates keep folding into the one `#gg:` commit on top until it is pushed. Before that commit, `EnsureGgJsonNotIgnored` (`tools/ensure_gg_json_not_ignored.dart`) verifies no gitignore rule excludes the state file — it is meant to be tracked, and an ignored one never shows up among the modified files, so the state would silently stop reaching the repository (and `git add` would refuse the explicitly named path in the publish bootstrap). Simple rules in the repo-root `.gitignore` (`.gg`, `.gg/`, `.gg/*`, a literal `.gg/gg.json`) are rewritten to the canonical `.gg/*` + `!.gg/gg.json` pair (see this repo's own `.gitignore` for why the bare directory pattern is unusable) and committed as `#gg: Stop ignoring .gg/gg.json`, with a `GgState.updateHash` transplant so recorded check results stay valid; a rule that cannot be rewritten safely (wildcards, nested ignore files, `.git/info/exclude`, a global `core.excludesFile`) throws with the manual fix. The check runs once per directory per process and is answered from a memo afterwards.

### `CommandCluster`

Used for commands that aggregate multiple sub-checks. For example, `CanCommit` (in `can/`) runs `analyze`, `format`, and `tests` as a cluster, short-circuiting on the first failure. Recording the success runs inside `GgProcessScope.shield`: a caller that cancels its process scope right after the checks passed must not stop the state between writing `.gg/gg.json` and committing it.

### One gg run at a time in a repository (`tools/repo_lock.dart`)

The commands of a cluster write into the repository — the coverage folder, generated test files, the state file and its commit. Two runs side by side (two terminals, a developer and an agent) spoil each other's results: one of them failed with »The test files exist but produced no coverage for their implementation file«, and both took three times as long. `CommandCluster.get` therefore runs its commands inside `RepoLock.use`. A second run logs »Another gg run works in `<repo>`. Waiting for it …«, waits, and then asks the recorded state again: when the first run checked this very state, the second prints the usual `✓` and runs nothing (`--force` runs the commands all the same). A run that finds its state recorded up front does not take the lock at all.

The lock is the file `.git/gg-run-lock` — for a worktree or submodule in the folder its `.git` file names —, so git neither tracks nor shows it. It holds one JSON line: the holder and an **expiry date**. The holder renews it every 10 s (`renewEvery`), and a lock that was not renewed for 30 s (`lifetime`) is free again, whatever became of its holder: a run that was killed or hangs never leaves a lock behind. Whoever takes such a lock after waiting for it says so (»The other gg run did not renew its lock on `<repo>` for 30s. Going on without it.«); a leftover that expired long ago is taken without a word. The lifetime is three renewals long, so a renewal that comes late on a busy machine does not open the lock under a run that is still at work. A holder that finds its lock taken at a renewal warns once and leaves the lock to the other run; when it is done it gives back only a lock that is still its own.

Reading the file and writing it anew is one step (`_change`), guarded by a lock of the operating system on the file that is held for that step only — a run that hangs holds none. Inside the process nothing gets in between because the step does not wait for anything. A wait ends with a `GgProcessCancelled` when the process scope of the caller is cancelled (`runInParallel` with `cancelOnError`). `use` inside of `use` for the same repository runs right away (a zone value names the locks held). A directory without `.git`, or a lock file that cannot be opened, is not protected: the work is done without the lock rather than not at all. Not covered: gg_test run on its own, and the flows that change a repository outside of a cluster.

Tests: `test/tools/repo_lock_holder.dart` is a process of its own for `repo_lock_test.dart` — it holds the lock like a gg run, gives it back on request or ends on the spot without giving it back, and it can hold the operating system lock of the file. `RepoLock(now:)` puts the lock on the clock of a test.

### Running tasks at the same time (`tools/parallel.dart`)

`runInParallel(count, task, ggLog, maxParallel, cancelOnError)` is how the family does the same thing for many repos at once. Every task gets a log of its own: what the first unfinished task logs reaches `ggLog` right away, what the tasks after it log is held back until it is their turn — so the output reads exactly like that of a loop, status lines that rewrite the line above included. Results come back in task order. A failure throws the error of the **first failed task in task order** (not the first in time) with its stack trace, and no further task starts. `cancelOnError: false` (tasks that change something) lets the running tasks finish and logs them; `cancelOnError: true` (checks) cancels the tasks after the failed one — each task runs in a gg_process `GgProcessScope`, whose cancel kills the processes it *started* (test runs) and refuses further ones — drops their output and throws as soon as the tasks before the failed one are done.

`GgParallelism` holds the limits — **one per kind of work, and gg is parallel by default**. Local work follows the machine; work at a remote gets small fixed numbers that do **not** grow with the machine, because a git host or a registry throttles by client, whatever it runs on, and a workspace of a hundred repos must never open a hundred connections.

| Limit | Default | For | Why this number |
| --- | --- | --- | --- |
| `heavy` | a quarter of the processors, 1–4 (`maxHeavy`) | test runs, analyzers, compilers | A test run takes half of the processors for its test files; side by side the runs share that half (`testFilesPerRun`), and with a quarter of the processors as the number of runs each keeps at least two test files. Fewer than eight processors — a usual CI runner — means one at a time, as before. The cap is what was measured (4 runs, 22 processors) and memory: about a gigabyte each for the analyzer and the test runner of a run. |
| `light` | the processors, 2–16 | tasks waiting for short processes, e.g. a few git calls | |
| `network` | 8 | reading from a remote: `git fetch`, `ls-remote`, registry lookups | A host limits how many connections a client opens at once and answers the surplus with dropped connections. |
| `pushes` | 4 | writing to a git remote: `git push` | A push makes the host check objects, run hooks and start pipelines; a burst from one client is what abuse limits look for. |
| `pullRequests` | 10 | creating pull requests through a host's API | What a host limits here is how many such requests **start** within a time, not how many run at once: GitHub takes 80 content-creating requests per minute and 500 per hour from a client and locks it out for minutes beyond that (»secondary rate limit«). That count is kept where the pull requests are created (gg_merge's `RequestLimit`, one for the whole process), so this number only says how many are under way at once. GitHub recommends sending them one after the other; the user asked for as many as the count allows (2026-11-14). |
| `publishes` | 4 | releases side by side | Each brings pushes, a pull request, a pipeline and an upload; the heavy part of a release is limited by `heavy` on top. |

`GG_PARALLEL=<n>` **sets** `heavy` and caps all others: `GG_PARALLEL=1` runs everything one after the other, `GG_PARALLEL=2` lets two test runs go at once. It never raises a limit for remote work. A limit is the first line of defence only: a request a remote turns away all the same is repeated after a wait by gg_git's `GitRetry`.

`GgParallelism.testFilesPerRun` is the other half of running test runs side by side: every test runner takes half of the processors for its test files, as if the machine were its own. Measured on 22 processors, Windows, twelve suites: four runs at once with 11 test files each made the suites that start many processes (git, `dart`) several times slower, and dozens of their tests ran into the 30 s timeout — one suite alone had eleven. With three test files per run not a single test timed out, and the twelve suites took 176 s instead of 254 s one after the other. A full `gg can commit --force` of eleven repos (pub get, analyze, format, tests) took 306 s one repo at a time and 156–170 s with `GG_PARALLEL=4`, three runs without a failure. So every run that shares the machine gets its share of what one run would take, rounded up (`Checks` hands it to gg_test's `Tests(concurrency:)`). **The share follows the runs that are under way, not the limit**: a command hands the heavy part of its tasks to `TaskSlots.heavy()`, and a test run started in one of these slots divides by the bodies that hold a slot or wait for one at that moment (at most the number of slots). The only repo to be tested — a ticket in which one repo changed, a single release — and every run outside of such slots (`gg one can commit`) is left to the test runner and gets the whole machine: the 39 test files of gg_git took 111 s with three at a time and 90 s with the runner's eleven. The gain of running side by side is modest because one test run of such a suite already keeps the machine busy starting processes; it comes from the suites and phases that do not. `GgParallelism.testTimeoutFactor` goes with it: a test of a run in heavy slots may take as many times its usual time as there are slots (`--timeout=<n>x` through `Tests(timeoutFactor:)`) — also when it is the only run right now, others may join it —, because sharing the machine made single suites up to three times as slow and a test that needs ten seconds alone ran into its 30. A test that hangs is still ended, after two minutes instead of half a minute. Outside of heavy slots the timeouts stay as they are.

`TaskSlots(n).use(body)` lets only `n` bodies run at the same time, whatever the number of tasks under way: tasks that are mostly light run with the `light` limit and hand their heavy part to shared slots, so a repo that only confirms an earlier result never waits behind a test run. `TaskSlots.heavy()` are the slots for that heavy part: `GgParallelism.heavy` of them, and the only ones `testFilesPerRun` and `testTimeoutFactor` answer for — other slots (a lock with one slot) say nothing about the machine, also when they are used inside of heavy ones. `waitForGitIndex` is what `runInParallel` waits for before a cancelled task's process is killed: a test run killed while git writes the index of its repository would leave `.git/index.lock` behind.

Before a command runs its repos in parallel, its per-repo collaborators must not keep the state of a run in their fields — one instance serves all tasks.

### Publish configuration

### Publish flow (`do_publish` + `do_configure_publish`)

A `--merge-only` run asks for **no version increment** at all: it releases nothing, so `do configure-publish` skips the prompt (its own `--merge-only` flag does the same) and writes no `version_increment`; `PublishConfig.resolveSingle`/`forRepo` accept a missing one via `requireVersionIncrement: false`.

`do publish` resolves all interactive input **up front** — version increment, merge message AND the delete-feature-branch decision (`delete_feature_branch` in the config; `configure-publish` asks it, `--[no-]delete-feature-branch` presets it, and the resolved value is persisted in the runtime file so a resume never re-asks): explicit parameters (the gg_multi flow) / CLI flags > `--config <path>` > an existing `<repo>/.gg/gg-publish.json` > an automatic interactive `do configure-publish` (which writes that file; `-m` presets the merge message and skips its prompt). No prompt ever sits between the irreversible publish steps. Every default prompt is guarded by `throwWhenNotATerminal` (from `gg_interact`, re-exported here): without a TTY it fails fast with an actionable message instead of hanging (CI, pipes). While the publish runs, per-step progress is recorded in the same `.gg/gg-publish.json` (`done_steps`: `prepare_version`, `publish_registry`, `merge`, `tag` — the three pushes and the feature-branch deletion are idempotent and always re-run; the deletion looks the remote ref up via `git ls-remote --heads origin <branch>` first and silently skips a branch that is already gone — e.g. deleted by the provider on a pull-request merge). After the `publish_registry` step, `do publish` waits until the version is actually **visible** on pub.dev/npm (gg_publish's `WaitUntilPublished`): it announces the wait including a status URL, logs progress and fails with a bounded timeout instead of hanging; the wait is idempotent (returns immediately once visible) and therefore always re-runs on resume. The file also records the feature `branch`, because a resumed run may find HEAD on the default branch already — but the persisted branch is only trusted **when resuming**; a leftover config-only file (a run that failed in `can publish`) must never pin a stale branch that a later publish would then delete. On full success the file is deleted.

Resume semantics: a leftover file with `done_steps` makes a plain `do publish` **refuse** (resume with `--continue`, discard with `--restart`) — unless the recorded `branch` is a _different feature branch_ than HEAD's: then the progress is a stale leftover of another publish that arrived with a copy of the repository (the file is gitignored, so copying a workspace carries it along) and is **discarded automatically** with a warning (a `--continue` refuses instead, with the same explanation), because trusting it would skip the current publish's version bump and registry upload and could delete the wrong feature branch; a mismatch while HEAD is on the default branch is _not_ stale — a resumed run whose merge already happened legitimately sits there; `--continue` (or the programmatic `resume: true` that `gg_multi do publish --continue` forwards) skips the done steps and skips `can publish` (the checks would fail on a half-published repo) — but it runs the hash-keyed `did commit` check, which survives gg's own bookkeeping commits and fails exactly when raw commits were added after the failure, so nothing unvalidated is ever published on a resume. When the merge step is already done, the feature-branch push at the start is skipped entirely — it would resurrect the possibly already-deleted remote feature branch; the remaining steps position themselves (bare-ref main push, tag-step checkout, feature branch for upload and restore). `do configure-publish` refuses to overwrite a file that carries `done_steps` (that would silently discard the resume state). `EnsurePublishConfigIgnored` (in `tools/`) guarantees the publish runtime files — `.gg/gg-publish.json` and the `pubspec_overrides.yaml` backup at `.gg/pubspec_overrides_backup.yaml` — are gitignored before they are first written (appending + committing the `.gitignore` change with a `GgState.updateHash` transplant so recorded check results stay valid); it first runs `EnsureGgJsonNotIgnored`, so a repository that git-ignored the whole `.gg/` folder is healed instead of crashing the `git add` of the bootstrap commit. Three GgState keys are written immediately **before** the merge, so the merge itself carries them into the default branch: `doCommit` (so a later `gg did commit` — CI, or a repo's own hook — accepts the release commit), `doPush` (so `gg did push` passes on a fresh CI checkout of main) and `didPublish` (read back by `gg did publish`; **not** written in merge-only mode, which releases nothing — and recorded once more at the end, when the restored workspace overrides changed the working tree). The merge comes first, the registry upload second — a refused merge stops the release while the registries are untouched. The merge and the main push are checkout-free (plumbing squash / bare-ref push — see gg_one_merge's CLAUDE.md); only the tag step checks main out, once it already carries the release. The former `doPublish`/`doMerge` keys are gone — the _step_ resume relies solely on `done_steps` in the git-ignored `.gg/gg-publish.json`, and `GgState` prunes the legacy keys (`doPrepareVersion`, `doPublishPubDev`, `doMerge`, `doPublishGit`, `doPublish`) from the tracked `.gg/gg.json` whenever it writes a state. The final tag push stays a raw `gitPush(pushTags: true)`.

All commands extend `DirCommand<T>` from `gg_args`. The primary logic lives in `get()`, and `exec()` simply delegates to it. `ggLog` (a `GgLog` function alias) is constructor-injected everywhere for testability and output capture.

## Testing Conventions

- 100% code coverage is required. Exempt lines with `// coverage:ignore-line` or `// coverage:ignore-start` / `// coverage:ignore-end`.
- Each implementation file must have a corresponding `_test.dart` in the mirrored path under `test/`.
- Mock classes are defined at the bottom of the **same file** as the class they mock, using `mocktail` and extending `MockDirCommand<T>`.
- Tests use `gg_git_test_helpers` (including the cached repo helpers) and `gg_capture_print`.
